# kit-builder: спецификация (черновик 1, 2026-10-06)

Исследования, на которых она стоит: `research-archetypes.md`, `research-evaluation.md` (рядом).

## 1. Цель

Кит официального маркетплейса, который помогает пользователю LADO:
- **создать** кит под свои задачи — от «ничего не знаю про LADO» до выпущенного тега `vX.Y.Z`;
- **оценить** любой кит (свой или чужой) до того, как пустить его в работу;
- **улучшать** существующий кит: по отчёту critic (v0.2.0), по метрикам сессий (этап 3);
- **сделать кит-расширение** к основному киту (этап 4).

Главный принцип: **самый простой кит, который решает задачу**. Новые роли, шаги и гейты
появляются только по требованию из интервью или по метрикам, и каждая часть кита знает, зачем
она есть.

## 2. Сценарии пользователя

| # | Кто | Что хочет | Ветка интервью |
|---|---|---|---|
| S1 | Есть устоявшийся процесс | Перенести его в LADO | «Перенос» |
| S2 | Ничего не знает про LADO | Получить работающий кит | «С нуля» (галерея архетипов) |
| S3 | Нужен узкий специализированный кит | Роли/скиллы под свою область | «С нуля» или «Перенос» + уточнение области |
| S4 | Есть основной кит | Дополнение к нему | `extend` (этап 4) |
| S5 | Есть кит (свой или из маркетплейса) | Понять, хорош ли он | `evaluate` |
| S6 | Есть свой кит (с BLUEPRINT.md или без) | Исправить найденное и выпустить новую версию | `improve`, ветка «Существующий кит» |

Интервью начинается с одного вопроса: «У вас уже есть процесс, который вы хотите перенести?»,
и дальше идёт по ветке.

## 3. Как пользователь начинает (инструкция в README кита)

```bash
lado kits add kit-builder -m official
mkdir my-kit && cd my-kit && git init && git commit --allow-empty -m init
lado start . --kit kit-builder
```
Дальше пользователь говорит с supervisor'ом в UI или терминале. Для оценки чужого кита сессию
можно начать в любом репозитории и назвать кит (имя установленного или путь к папке).

## 4. Состав кита

### Роли
| Роль | Что делает | Права |
|---|---|---|
| `supervisor` (ведущий) | Интервью, blueprint, разговор с человеком, выпуск | пишет blueprint, коммитит, ставит тег |
| `author` | Пишет файлы кита по утверждённому blueprint | пишет в репозиторий кита |
| `critic` | Оценка кита (слои a и b), отчёт | только чтение (+ файл отчёта) |
| `tester` | Пробные прогоны (этап 2) | песочница |

MVP: `supervisor`, `author`, `critic`. Сам kit-builder проходит свой бюджет сложности.

### Flows
**`create`** (MVP):
```
design (supervisor) → design_ok (гейт: approval)
  → build (author) → evaluate (critic, max_visits 3; changes → build)
  → release_ok (гейт: approval) → release (supervisor) → done
```
- `design`: интервью раундами (вопрос + контекст + рекомендация), выбор архетипа или разбор
  процесса пользователя, `BLUEPRINT.md` (раздел 5). Заметка шага — blueprint целиком.
- `build`: кит по blueprint; на повторном визите — правки по отчёту critic.
- `evaluate`: слои a+b (раздел 6); `approved` или `changes` со списком.
- `release`: версия в `kit.yaml`, `lado kits check . --tag vX.Y.Z` = OK, коммит и тег.
  Push и PR в маркетплейс — только по явному «да» человека; supervisor даёт готовый текст PR
  (строка `marketplace.yaml` + строка таблицы README).

**`evaluate`** (MVP): один шаг `evaluate` (critic) → `done`. Вход — кит (папка или имя
установленного), выход — отчёт.

**`improve`** (v0.2.0): доработка кита из репозитория сессии по отчёту critic.
```
assess (critic) → triage (supervisor) → plan_ok (гейт: approval)
  → build (author) → evaluate (critic, max_visits 3; changes → build)
  → release_ok (гейт: approval) → release (supervisor) → done
```
- `assess`: полная оценка текущей версии (как `evaluate`); если в задаче назван отчёт этой
  же версии — берётся он.
- `triage`: supervisor с человеком по ветке «Existing kit» скилла `kit-interview`: если нет
  `BLUEPRINT.md` — восстановить его из ролей и flows, спрашивая только о спорном; по каждой
  находке и «Questions for the human» — решение; жёлтые меры — оставить с обоснованием или
  убрать; строки в журнал (раздел 5 BLUEPRINT). Заметка — план изменений и целевая версия
  (patch — только текст, minor — состав или поведение).
- `build`, `evaluate`, `release` — как в `create`; общие правила шагов живут в ролях,
  `do` ссылаются на них. `blocked` у author → `triage`.

Этап 3 добавит перед `assess` сбор метрик сессий (слой d), и факты для журнала будут
браться и из них.

**`extend`** (этап 4): как `create`, но `design` читает основной кит, а результат — кит без
`supervisor` (только роли и/или скиллы), чтобы не менять, кто ведёт сессию (правило LADO
«One lead, one rule»).

### Скиллы (свои)
| Скилл | Кто | Содержание |
|---|---|---|
| `kit-interview` | supervisor | ветки интервью, банк вопросов, формат раундов, как разбирать материалы пользователя (CLAUDE.md, свои скиллы, описание процесса, статусы задач трекера) в роли/шаги/гейты |
| `kit-archetypes` | supervisor | 9 архетипов (раздел 7): состав, flow, когда брать, сложность |
| `lado-kit-format` | все | формат кита LADO кратко + правила (нейтральность к провайдеру, пути через `${KIT_DIR}`, one lead, `needs`, гейты, `max_visits`); источник истины — `lado kits check`, скилл на него ссылается |
| `kit-budget` | critic, supervisor | бюджет сложности + скрипт подсчёта (раздел 6a) |
| `kit-rubric` | critic | рубрика 12 критериев и формат отчёта (раздел 6b) |
| `kit-trial` | tester | этап 2 |
| `kit-retro` | critic | этап 3: метрики и их чтение |

Общие скиллы (grilling, writing-for-agents) — через `dependencies.skills`, не копией.

## 5. BLUEPRINT.md (в корне репозитория создаваемого кита)

Единственное место, где записано «зачем» каждой части кита; его читают `build`, `evaluate`,
`improve`.
1. **Требования** R1..Rn: что пользователь хочет получить (его словами + уточнения).
2. **Исходная точка**: архетип или описание перенесённого процесса.
3. **Трассировка**: каждая роль, шаг flow, гейт, скилл, MCP-сервер → какие R он закрывает.
   Элемент без R — кандидат на удаление (critic помечает).
4. **Бюджет сложности**: счёт по разделу 6a и обоснование каждого превышения.
5. **Журнал изменений «изменение ← факт»** (заполняет `improve`).

## 6. Оценка кита

### a) Статика (бесплатно, детерминированно)
- `lado kits check` — формат и правила LADO (графовые проверки flow — в ядре, см. раздел 9).
- Скрипт `kit-budget`:

| Мера | Зелёный | Жёлтый (нужно обоснование) | Красный |
|---|---|---|---|
| Рабочие роли (кроме supervisor) | ≤ 3 | 4–5 | > 5 |
| Рабочие шаги в flow | ≤ 5 | 6–8 | > 8 |
| Гейты в flow | ≤ 2 | 3 | > 3 |
| Слов в промпте роли | ≤ 800 | 801–1500 | > 1500 |
| Своих скиллов | ≤ 5 | 6–10 | > 10 |
| MCP-серверов | ≤ 2 | 3–4 | > 4 |

  плюс одинаковые абзацы в разных ролях и `do` шагов (одно правило — одно место).
- Пороги — стартовые; их пересматриваем по опыту.

### b) Ревью текста по рубрике (critic)
12 критериев: границы ролей; полнота передачи между шагами (что в заметке для `needs`);
критерий «готово» у каждого шага и условие каждого исхода; независимая проверка до конца
flow; противоречия (в роли, между ролью и `do`, с инструкциями LADO); дубли; когда звать
человека; поведение циклов на повторном визите (RESOLVED / STILL OPEN); лаконичность и «почему»;
описания скиллов (когда применять, чем отличается от соседних); нейтральность к провайдеру;
безопасность (ничего необратимого без гейта).
Вердикт по каждому критерию с цитатой из файла; 3 прохода, в отчёт — только повторившиеся
находки. Это кандидаты для человека, не pass/fail.

### Отчёт
Файл `kit-reports/<kit>-<версия>-<дата>.md` в репозитории сессии: карточка (бюджет по таблице,
итог по слоям), находки с цитатами и файлами, «что исправить первым» (≤ 5 пунктов). Позже —
артефакт LADO (этап 7 ROADMAP).

### c) Пробные прогоны (этап 2)
Фиксированные сценарные задачи в песочнице; кит против базы (прошлая версия или `default`)
на том же провайдере; гейты отвечает человек («честный прогон»). Оценка сначала проверками
(тесты, run дошёл до конца, кругов ревью ≤ N, без `flow-set`), судья — только для качества
дизайна. Модель не задаём; перед прогоном — предупреждение о времени и стоимости.

### d) Метрики реальных сессий (этап 3)
Из данных LADO: доля завершённых/отменённых run, время run; визиты по шагам и возвраты;
отказы на гейтах; `flow-set` (самый сильный сигнал «flow не подходит»); ожидание человека;
ответы «только в терминале»; пустые заметки; failed-сообщения; занятость ролей как прокси
стоимости; привязка к шагу/роли. Тренды и выбор сценариев для c), не доказательство.

## 7. Галерея архетипов
(воркер-роли / шаги / гейты)
0. **Соло** 1/1/0–1 — стартовое предложение.
1. **Соло + ревьюер** 2/2/1.
2. **Фича с гейтом дизайна** 3/3/2.
3. **Исследование и отчёт** 2/4/1.
4. **Параллельный веер** 2/4/1 — только для независимых частей.
5. **Сортировка входящих** 2–3/2/0–1.
6. **Документация/контент** 2/3/2.
7. **Инцидент/ops** 2/3/2.
8. **Поиск бага** 2/3/1.
Групповой чат и «рой» без ведущего не предлагаются без явной просьбы.

## 8. Этапы
1. **MVP**: `create` + `evaluate` (слои a, b), архетипы, интервью, BLUEPRINT, инструкция,
   выпуск тега. Публикация kit-builder в маркетплейс.
2. **Пробные прогоны**: роль `tester`, `kit-trial`, слой c.
3. **Метрики и `improve`**: слой d, журнал «изменение ← факт».
4. **`extend`**.

**v0.2.0** (между MVP и этапом 2, по работе над китом lado-dev): flow `improve` по отчёту
critic (раздел 4) и ветка «Existing kit» в `kit-interview` с восстановлением `BLUEPRINT.md`
у кита без него. Метрики сессий для `improve` остаются на этапе 3.

## 9. Что нужно от ядра LADO (отдельные задачи в репозитории lado)
- **L1 (до MVP)**: графовые проверки flow в `lado kits check`. Уже есть: недостижимые
  состояния, «ни один end не достижим», outcome/needs на несуществующее состояние, роль шага
  не из кита. Добавить: состояние, из которого не дойти до `end` (ловушка); цикл без
  `max_visits` или гейта; `needs` на состояние, которое не может быть раньше; роль кита, не
  участвующая ни в одном шаге (предупреждение).
- **L2 (этап 2, проверить)**: может ли агент запустить пробную сессию LADO в песочнице
  (отдельный `LADO_HOME` и tmux-сокет) и наблюдать её; что мешает.
- **L3 (этап 3)**: машиночитаемый экспорт метрик (`lado stats --json` или `lado log --json`).
- Не планируем: выбор модели, автоответ на гейты.

## 10. Вне рамок
Автопубликация в маркетплейс без «да» человека; выбор модели; автоответчик на гейты;
генерация MCP-серверов (кит-билдер может подключить существующий, но не пишет код сервера).
