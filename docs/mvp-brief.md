## Решения, которые уже приняты

- Имя кита `kit-builder`, репозиторий `ladohq/kit-builder`.
- `dependencies.lado: ">=0.23"` (с 0.23.0 `lado kits check` проверяет граф flow).
- В MVP входят роли `supervisor` (ведёт сессию, `supervisor: supervisor` в kit.yaml), `author`
  и `critic`; flows `create` и `evaluate`; свои скиллы `kit-interview`, `kit-archetypes`,
  `lado-kit-format`, `kit-budget`, `kit-rubric`. Роль `tester`, flows `improve` и `extend`
  в MVP не входят.
- Общие скиллы (grilling, writing-for-agents) подключаются через `dependencies.skills`, без
  копирования: `mattpocock-skills` из `https://github.com/mattpocock/skills@v1.2.3`, нужные
  папки — по образцу kit.yaml кита lado-dev.
- Файлы кита (kit.yaml, роли, flows, скиллы, README) пишутся по-английски: кит рассчитан на
  всех пользователей маркетплейса. С человеком говори по-русски.
- Кит должен укладываться в свой же бюджет сложности (спека 6a); выход за зелёную зону
  обоснуй в `BLUEPRINT.md` самого kit-builder.

## Как работать в этой сессии

В ките `default` flows нет, поэтому процесс задачи такой:
1. Воркер получает от тебя бриф задачи: цель, файлы, AC из этого документа и способ
   проверки. Он работает в своей ветке, пишет тесты до кода там, где есть код (скрипт
   бюджета), и отчитывается по каждому AC с выводом проверок.
2. Ветку проверяет другой воркер, только читая, без правок: смотрит AC, спеку и
   `git diff main...<ветка>`. Вердикт: мержить или список замечаний. Больше трёх кругов не
   делай: тогда решает человек.
3. Перед мержем спрашиваешь человека: одна строка, что сделано и вердикт ревьюера. Мержишь
   только после «да», затем `finish_worker`.
4. Замечание вне задачи записывай в `BACKLOG.md` этого репозитория. Баг или неудобство в
   самом LADO запиши туда же с пометкой `[lado]`: их перенесут в репозиторий LADO.

Порядок задач: T1, затем T2 и T3 (их можно вести параллельно), затем T4.

## Задачи

### T1. Каркас и статика
- AC1.1 `kit.yaml`: name, version `0.1.0`, description, `supervisor`, dependencies (lado,
  skills); пустых ролей и flows нет.
- AC1.2 Скилл `lado-kit-format`: формат кита и правила LADO (нейтральность к провайдеру,
  пути только через `${KIT_DIR}` / `${SKILL_DIR}`, правило «один ведущий», `needs`, гейты,
  `max_visits`). Источником истины называет `lado kits check`; правил ядра не пересказывает,
  если команда их уже проверяет.
- AC1.3 Скилл `kit-budget` со скриптом: на вход папка кита, на выход каждая мера из таблицы
  спеки 6a со значением и зоной (зелёная/жёлтая/красная), плюс одинаковые абзацы в разных
  ролях и в `do` шагов. Код выхода не 0 при красной зоне. Скрипт работает на чистой машине
  с одним LADO: зависимости объявлены (например, PEP 723 и `uv run --script`) или скрипт
  обходится стандартной библиотекой. Абсолютных путей нет.
- AC1.4 У скрипта есть тесты на маленьких китах-фикстурах: на каждую меру и на каждую из
  трёх зон хотя бы по одному случаю, отдельный случай на дубли. Тесты запускаются одной
  командой, она записана в README.
- AC1.5 `lado kits check .` проходит (до тега без `--tag`, предупреждения выписаны в отчёт).

### T2. Оценка: роль `critic`, скилл `kit-rubric`, flow `evaluate`
- AC2.1 `agents/critic.md`: роль только читает, пишет один файл отчёта; на входе папка кита
  или имя установленного кита (как найти его папку: `lado kits show`).
- AC2.2 `kit-rubric`: 12 критериев из спеки 6b, у каждого — что считать нарушением; формат
  вердикта с цитатой и файлом; правило трёх проходов, в отчёт попадают только
  повторившиеся находки.
- AC2.3 Формат отчёта по спеке («Отчёт»): `kit-reports/<kit>-<версия>-<дата>.md`, карточка
  бюджета (вывод скрипта из T1), находки, «что исправить первым» не больше 5 пунктов.
- AC2.4 `flows/evaluate.yaml`: шаг `evaluate` (critic) → `done`; `lado kits check .` проходит
  без ошибок графа.
- AC2.5 Проверка на живом ките: critic оценивает кит lado-dev (путь выше), отчёт
  прикладывается к отчёту задачи. Ревьюер проверяет, что у каждой находки есть цитата из
  реального файла.

### T3. Создание: `supervisor`, `author`, скиллы интервью и архетипов, flow `create`
- AC3.1 `agents/supervisor.md`: ведёт интервью раундами (вопрос, контекст, рекомендация),
  начинает с вопроса «Есть ли у вас процесс, который вы хотите перенести?» и идёт по ветке
  («Перенос» или «С нуля»); пишет `BLUEPRINT.md`; push и PR в маркетплейс делает только
  после явного «да» человека и даёт готовый текст PR (строка `marketplace.yaml`, строка
  таблицы README).
- AC3.2 `kit-interview`: ветки, банк вопросов, как разбирать материалы пользователя
  (CLAUDE.md, свои скиллы, описание процесса, статусы задач трекера) в роли, шаги и гейты.
- AC3.3 `kit-archetypes`: 9 архетипов из спеки 7 (состав, flow, когда брать, сложность);
  стартовое предложение — «Соло»; групповой чат и рой без ведущего не предлагаются без
  явной просьбы.
- AC3.4 Шаблон `BLUEPRINT.md` с пятью разделами из спеки 5; в разделе «Трассировка» каждый
  элемент кита связан с требованием R.
- AC3.5 `agents/author.md`: пишет кит по утверждённому blueprint; на повторном визите
  исправляет по отчёту critic и отмечает каждую находку как исправленную или нет, с
  причиной.
- AC3.6 `flows/create.yaml` — граф из спеки 4 (design → design_ok → build → evaluate,
  `max_visits: 3`, при `changes` обратно в build → release_ok → release → done), `needs`
  передаёт blueprint в build и evaluate; `release` проверяет `lado kits check . --tag vX.Y.Z`
  перед тегом. `lado kits check .` проходит без ошибок графа и без предупреждения «роль ни
  в одном шаге».

### T4. Самопроверка, README, выпуск
- AC4.1 `BLUEPRINT.md` самого kit-builder: требования R из спеки, трассировка каждой его
  части, бюджет по выводу скрипта с обоснованием каждой жёлтой меры.
- AC4.2 kit-builder оценивает сам себя flow'ом `evaluate`; находки из «что исправить первым»
  исправлены или явно отложены в BACKLOG.md с причиной.
- AC4.3 README: что делает кит, установка и старт (спека 3, с `lado kits add kit-builder -m
  official`), оба flow, команда тестов скрипта, требование `lado >= 0.23`.
- AC4.4 Сквозной прогон руками: в пустом временном репозитории с отдельными `LADO_HOME` и
  `LADO_TMUX_SOCKET` (`lado kits add <путь к kit-builder>`, затем
  `lado start <tmp> --kit kit-builder`) запускается `create` для простого кита, человек
  проходит гейты, на выходе кит, который проходит `lado kits check`. Что сломалось или мешало — в BACKLOG.md. Этот прогон тратит модель:
  перед запуском предупреди человека и спроси согласия.
- AC4.5 `lado kits check . --tag v0.1.0` проходит; коммит и тег `v0.1.0` локально. Push в
  `ladohq/kit-builder` и PR в маркетплейс — только после «да» человека, и это вопросы
  человеку, а не тебе.

## Вне рамок
Роль `tester` и пробные прогоны (слой c), метрики и `improve`, `extend`, генерация
MCP-серверов, выбор модели, автоответы на гейты (спека 8 и 10). Изменения в ядре LADO: если
без них не обойтись, запиши в BACKLOG.md с пометкой `[lado]` и скажи человеку.

## Готово, когда
T1–T4 смержены в main этого репозитория, `lado kits check . --tag v0.1.0` проходит,
тесты скрипта зелёные, тег `v0.1.0` стоит локально, а человек получил одну строку итога и
вопрос про push и PR в маркетплейс.
